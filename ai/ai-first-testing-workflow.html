AI-FIRST TESTING / READING NOTE

收斂、探索與可重複執行

AI 不應取代測試框架。人決定什麼才是正確，AI 探索怎麼驗證，固定程式碼負責廉價、穩定、反覆執行。

03 探索AI 實際找出操作與驗證步驟

角色分工

Brain領域專家確認條件、風險、錯誤優先順序與預期結果。
GPUAI 展開候選情境、探索 API／UI 操作、整理 session log、產生 Test Code。
CPUPest、xUnit、Playwright 等固定程式由 CI 或排程反覆執行。
測試只能證明已定義且已涵蓋的條件目前符合預期，不能證明整個程式完全無誤。

Decision Table：不是自動答案，而是把問題攤開

組成

  • Criteria：影響結果的條件
  • Action：系統應採取的行為
  • Rule：條件組合與預期結果

人工校正

  • 成功、全面失敗、部分成立
  • 上下限與邊界外
  • 不可能狀態
  • 多錯誤的優先順序
  • 條件相依

AI 可以產生第一版表格，但是否符合實際領域規則，必須由人確認。Decision Table 也不能單獨解決組合爆炸，仍要搭配等價類別、邊界值、Pairwise、風險導向與歷史缺陷。

抽象 Test Case

核心：把「測什麼」與「怎麼操作」分離。

Test Case 只保留 Given、When、Then，不寫死 endpoint、HTTP Header、按鈕、selector 或測試框架。同一個商業情境才能搭配 OpenAPI、Web UI 或 App 規格，分別生成 API、Web、App 測試。

REST API、Web UI、Android、iOS 是操作介面；Pest、PHPUnit、Playwright、Appium 是測試框架或工具，不能混為一談。

AI 探索到底在做什麼

探索不是再找一次漏測情境，而是針對已確定的 Test Case 找出：

  • 如何建立及清理測試資料
  • 如何登入、取得授權、呼叫 API 或操作 UI
  • 結果要從回應、資料庫、事件、Queue 或外部呼叫的哪裡驗證
  • 如何隔離資料與穩定重現

AI 根據規格與失敗回應反覆修正。Session log 讓人審查探索是否正確，也成為產生 Test Code 的操作範例。探索不是 CI/CD 每次都要執行的工作。

舊方法與改良流程的真正差異

Vibe Testing

每次都讓 AI 重新理解案例、操作系統、觀察結果並判斷。成本來自整個 Agent 推論與工具呼叫，不是「啟動測試」本身。

固定 Test Code

AI 只在建立階段探索並產生程式。之後由 CI 直接執行固定 assertion，模型不參與回歸測試。

文章的估算是從 40,000 次 AI 任務，改成 400 次探索、400 次程式碼產生，以及 40,000 次一般 CPU 測試。觸發者仍可都是 CI；改變的是執行者。

MCP 的建立理念

  • MCP 是 AI 與受測系統之間的受控工具層，不是測試框架。
  • 登入、API 呼叫、狀態查詢、資料準備與清理要有結構化輸出。
  • 保留 session log、規格快照與稽核紀錄。
  • 限制可操作環境、動作、資料範圍與敏感資訊。
  • 不能把無邊界的管理員 API 直接交給 Agent。

無障礙也是 Agent 的操作介面

Playwright MCP 可利用語意化 HTML、ARIA 與 Accessibility Tree 提取精簡結構，避免完整 HTML 塞滿前後文，也比視覺辨識與座標點擊穩定。

  • 使用正確的 button、label、input、nav
  • 欄位有明確 label
  • 按鈕與連結有可理解名稱
  • 錯誤與狀態能由 ARIA 表達
  • 不只依賴顏色、座標或圖示

無障礙的主要服務對象仍是人；AI Friendly 是相同語意基礎帶來的延伸效益。

正式導入時原文沒有處理完的部分

Test Oracle

HTTP 200 不代表完整成功。還要驗證資料、事件、Queue、外部呼叫、回滾與冪等性。

可重複性

固定時間、亂數、非同步、外部服務、資料隔離與環境差異。

規格漂移

需求變動後，要判斷 Decision Table、Test Case、操作規格或 Test Code 哪一層需要更新。

維護責任

AI 降低首次建立成本，但不會消除 AC、規格、session log 與程式碼的同步成本。

套用到 Laravel 金流專案

第一個試點適合選「代付訂單建立前置驗證」，條件包含商戶、IP、簽章、timestamp、nonce、錢包、幣種、餘額、通道與限額。

  1. 選一項 AC
  2. AI 產生第一版 Decision Table
  3. 領域人員確認條件與預期結果
  4. 收斂為 5～15 個抽象 Test Case
  5. 探索 2～3 個高價值案例
  6. 依 Laravel route、Form Request、Service、Factory、Seeder 與既有 Pest 產生 Test Code
  7. 人工審查 assertion、隔離與副作用
  8. 納入 CI
  9. 經過數次需求變更後，再判斷是否建立 MCP
不要先開發 TestKit 或 MCP。只有登入、簽章、建立商戶、調整錢包、查詢事件與清理資料等工作反覆出現時，才值得封裝。
