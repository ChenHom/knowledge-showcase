# Decision Table Playbook 文件設計

#decision-table #playbook #ai-assisted-testing #document-design

## 這是什麼

這份設計定義一篇可重播的 Decision Table 操作手冊。目標不是再介紹 Decision Table，而是讓開發者、QA、PM 或領域人員從同一類需求輸入出發，按照固定步驟使用 AI、完成領域審查，產出結構一致且可直接轉成 Test Case 的表格。

## 核心結論

正式文件採用分階段 Playbook。每個階段固定包含輸入、操作、AI Prompt、產出格式、人工檢查及完成條件；未通過完成條件，不得進入下一階段。

AI 負責整理、展開與檢查候選內容，領域人員負責確認業務事實、錯誤優先順序與 Test Oracle。文件不得暗示只靠相同 Prompt 就能保證相同品質；一致性來自固定輸入契約、中間產物、審查門檻與最終核可。

## 目標讀者與使用前提

目標讀者包含開發者、QA、PM 與領域人員，不要求事先熟悉 Decision Table。

開始操作前至少需要一條 Acceptance Criteria。若已有業務規則、詞彙表、限制、錯誤碼、範例或既有測試，必須一起提供；缺少的領域答案標記為 `OPEN-*`，不可由 AI 依慣例自行補齊。

## 文件輸出

核可後要建立的正式操作手冊為 `notes/ai/decision-table-playbook.md`。本設計文件只定義它的內容、流程與驗收方式，不取代正式手冊。

操作者完成 Playbook 後，應得到：

1. 經確認的需求輸入表。
2. 已確認事實與待確認問題清單。
3. Conditions、Actions 與 Oracle 定義。
4. 候選 Rules 與刪留紀錄。
5. 經領域人員核可的 Decision Table。
6. Rule 對 Test Case 的一對一對照。
7. 審查紀錄及限制說明。

## 文件主流程

### 階段 0：判斷是否適用

- 輸入：要驗證的需求或流程。
- 操作：判斷結果是否主要由有限的條件組合決定。
- 產出：`適用`、`部分適用` 或 `不適用`，並記錄理由。
- 人工檢查：若主要問題是效能、壓力、長時間序列、複雜狀態機或高併發異常，不可只用 Decision Table 表達。
- 完成條件：已界定 Decision Table 能處理的範圍及必須由其他方法補足的範圍。

### 階段 1：建立輸入基線

- 輸入：AC、業務規則、限制、資料範例及既有規格。
- 操作：拆成名詞、可觀察事實、規則、範例及未知事項。
- AI Prompt：只能整理來源內容；每項結論必須指向來源，無來源者列為 `OPEN-*`。
- 產出：需求輸入表與 open questions。
- 人工檢查：移除 AI 自行補入的慣例，請領域人員回答會改變結果的問題。
- 完成條件：沒有未標記的假設；未解問題不會被當成既定規則。

### 階段 2：產生候選 Conditions

- 輸入：已確認的事實、規則與未知事項。
- 操作：列出會改變結果的最小條件集合。
- AI Prompt：為每個 Condition 提供名稱、資料型別、值域、來源及它會影響的結果；不得把結果或實作步驟寫成 Condition。
- 產出：Condition catalog。
- 人工檢查：Condition 必須能被安排或觀察；避免「有效」「正確」「正常」等循環定義。
- 完成條件：每個 Condition 都有明確值域、來源及業務意義，重複或派生條件已刪除。

### 階段 3：定義 Actions 與 Test Oracle

- 輸入：業務承諾、錯誤碼、公式、副作用與 Conditions。
- 操作：列出每種結果需要驗證的可觀察行為。
- AI Prompt：為每個 Action 提供精確值、公式、狀態、錯誤碼或副作用；禁止只寫「成功」「處理正確」。
- 產出：Action／Oracle catalog。
- 人工檢查：確認結果能被測試系統觀察，且同時涵蓋應發生與不應發生的副作用。
- 完成條件：每個 Action 都能直接轉成 assertion，Oracle 的來源已由領域人員確認。

### 階段 4：生成候選 Rules

- 輸入：Condition 與 Action／Oracle catalogs。
- 操作：先機械展開可能組合，再標記不可能、重複、無業務意義及需要人工回答的組合。
- AI Prompt：不得靜默刪除組合；每個省略或 `-` 都要說明是無關條件、短路規則或不可達狀態。
- 產出：未收斂的候選 Decision Table。
- 人工檢查：檢查條件相依、短路與多個錯誤同時成立時的優先順序。
- 完成條件：每個候選組合都有結果或明確的待決標記。

### 階段 5：用邊界與風險收斂

- 輸入：候選 Rules、風險、歷史缺陷及使用頻率。
- 操作：保留正常路徑、空值、最小與最大合法值、門檻前後、最小非法值、混合情境及高風險案例。
- AI Prompt：為每個 Rule 寫出測試企圖、保護的風險及與相鄰 Rule 的差異。
- 產出：精簡 Rules 與刪留紀錄。
- 人工檢查：若兩個 Rule 的測試企圖相同，確認是否合併；若重要風險沒有 Rule，補上案例。
- 完成條件：每個保留 Rule 都有獨特測試企圖，每個高風險業務承諾至少被一個 Rule 覆蓋。

### 階段 6：驗證語意、公式與算術

- 輸入：收斂後的 Decision Table。
- 操作：分開執行業務語意、公式、逐列算術、邊界及跨列一致性檢查。
- AI Prompt：以已確認公式重新計算每一列，列出計算過程；另外提出最小反例，但不得修改業務答案。
- 產出：驗證報告與修正版表格。
- 人工檢查：領域人員核對語意與錯誤優先順序；計算結果應以獨立方式重算，不沿用初次生成值。
- 完成條件：所有差異已修正或記錄為待決問題，沒有只靠 AI 自我宣告正確的結果。

### 階段 7：完整性與可測性審查

- 輸入：修正版表格與需求輸入表。
- 操作：由 Rule 反查需求，再由每項需求正查 Rules。
- AI Prompt：找出未覆蓋規則、無來源 Condition、無法觀察的 Action、矛盾結果及不可達組合。
- 產出：追蹤矩陣與審查清單。
- 人工檢查：確認表格只主張已知範圍，不把「未列出」誤寫成「不可能」。
- 完成條件：所有重要需求可追蹤到 Rule，所有 Rule 可追蹤到來源與 Oracle。

### 階段 8：領域核可與凍結

- 輸入：Decision Table、驗證報告、追蹤矩陣及 open questions。
- 操作：領域負責人核可版本，記錄日期、範圍、限制及仍待確認事項。
- 產出：有版本識別的正式 Decision Table。
- 人工檢查：未核可或仍會改變預期結果的問題，不得隱藏在備註中。
- 完成條件：核可者、版本、來源、限制及待決事項齊全。

### 階段 9：轉成 Test Cases

- 輸入：已凍結的 Decision Table。
- 操作：每個 Rule 產生一個 Given／When／Then Test Case；需要合併或拆分時記錄理由。
- AI Prompt：只能使用表格內的輸入與 Oracle，不加入 API endpoint、DOM selector 或框架細節。
- 產出：Rule-to-Test-Case mapping 與抽象 Test Cases。
- 人工檢查：測試輸入與預期結果逐欄對回原 Rule。
- 完成條件：每個 Rule 都有對應測試，沒有測試引入表格外的新業務答案。

## 固定產物格式

正式文件要提供可直接複製的模板：

- 需求輸入表：項目、內容、來源、狀態。
- Open questions：ID、問題、影響、負責人、狀態。
- Condition catalog：ID、定義、型別、值域、來源。
- Action／Oracle catalog：ID、定義、預期值或公式、觀察方式、來源。
- Rule table：Rule、Conditions、Actions、測試企圖、風險、狀態。
- 刪留紀錄：候選 Rule、保留或刪除、理由。
- 驗證報告：檢查類型、Rule、計算或證據、結果、處置。
- 追蹤矩陣：需求、規則、Rule、Oracle、Test Case。

## 最終品質門檻

一張表只有同時符合以下條件才算完成：

- 每個 Condition 可安排或觀察，且有明確值域。
- 每個 Action 可直接轉為 assertion。
- 每個 Rule 有測試企圖，不是為湊排列組合而存在。
- 邊界前、邊界值及邊界後有適當覆蓋。
- 不可能組合、短路條件與 `-` 都有理由。
- 多錯誤情境的優先順序已核可。
- 公式與逐列結果經獨立重算。
- 所有重要業務承諾可追蹤到至少一個 Rule。
- 所有 Rule 可追蹤到需求來源及 Oracle。
- 未確認事項明確可見，沒有被 AI 默認補齊。
- 領域負責人已核可版本及適用範圍。

## 完整案例設計

正式文件使用購物車案例貫穿所有階段，保留 AI 初版的布林 Conditions，展示它為何無法直接安排測試；再逐步改成商品數量、優惠組數、原價、折扣、結帳金額與允許結果。

案例必須展示至少兩種真實修正：

1. 將「第二件六折」從錯誤的「第二件以後皆六折」修正為每兩件一組。
2. 逐列重算並修正混合商品總額。

案例除了最終表格，也要保留每一輪修改理由，讓讀者學會判斷，而不是複製答案。

## 錯誤處理與停止條件

- AC 缺少會改變結果的規則：停止展開，建立 open question。
- 領域人員無法確認 Oracle：保留候選 Rule，但不得標記完成或產生正式測試。
- 組合數量爆炸：先按等價類別、邊界與風險收斂；仍過大時拆成多張聚焦不同決策的表。
- 需求主要是時間序列、狀態轉移或併發：改用狀態機、timeline simulation 或 property-based testing 補足。
- AI 多次產生不同答案：回到來源與公式，不以投票或多數答案決定業務事實。

## 文件驗證方式

正式文件完成後，以同一份 AC 進行兩次乾跑：一次由熟悉需求者操作，一次由未參與撰寫者只依 Playbook 操作。比較兩次產物是否具備相同欄位、可追蹤性、邊界覆蓋與核可紀錄；差異若來自文件歧義，必須修正文案或模板。

此外使用一個非購物車案例進行遷移驗證，避免流程只對原文範例有效。建議採用現有的付款 callback 案例，檢查 Playbook 是否能導出冪等檢查早於訂單狀態檢查的 Rule 順序。

## 限制與來源邊界

原始文章省略了作者修改第一版 Decision Table 時的完整對談。正式文件必須清楚區分：文章直接展示的初版、定稿與錯誤案例，以及根據兩者差異整理出的可重播方法。不得把重建出的中間步驟描述為作者公開的逐字流程。
