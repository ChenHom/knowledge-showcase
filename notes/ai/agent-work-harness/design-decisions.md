# 設計決策與它們的理由

#ai #agent #architecture #decision-record #yagni

## 這是什麼

Agent Work Harness 開發過程中的關鍵決策，以及每個決策背後的取捨。
重點記「為什麼這樣決定」與「什麼情況下該反過來做」——
只記結論的決策紀錄，過三個月就沒人知道它還成不成立。

## 核心結論

> 只加已經有真實失敗案例證明需要的機制。

這句話容易說難做。難的地方在於：設計一個機制的時候，你會清楚看見它能解決什麼問題 ——
包括那些還沒發生的問題。抵抗那個誘惑需要一條明確的判準，而不是自制力。

## 邊界類決策

### 不做 RAG，即使這是一個 context 系統

Agent Runtime 本身就是一個會主動檢索的東西（它會 grep、讀檔、看 git history）。
如果外層再加一套 embedding → 向量檢索 → 摘要 → 塞進 prompt，會得到：
重複檢索、過期摘要、context 衝突、prompt 膨脹、來源難以追溯。

改成 **pointer-first**：只給位置，讓 Agent 自己讀。

實測結果：36.6k 行的專案，prompt 維持在 2.0–2.4 KB，零重試。
換到完全陌生的 domain（Python / 向量檢索）也一樣。

**什麼情況該反過來：** 如果多數工作都因為 Agent 找不到入口而失敗。
但要先分清楚是「入口設定不好」「Agent 檢索能力不足」還是「需求本身太模糊」——
直接跳到 RAG 是最貴的答案。

### 不做信心分數，把組成攤開

把 evidence 的可信度壓成一個 `0.87` 會丟失資訊，而且沒人知道那個數字怎麼來的。
改成把組成攤開：執行了幾個、跳過幾個、基準是多少、哪些是既有測試、哪些是這次新增的。

判斷權留給人，而人需要的是組成不是分數。

### 不用第二個 LLM 判斷 evidence 可不可信

那只是把不可驗證性搬到另一個地方，還多一層。

同理：不用 LLM 判斷「需求是否達成」。語意正確性機械上不可判定，
正確做法是**誠實命名**而不是假裝解決 —— 用「依 evidence 契約接受」而不是「成功」。

### 名字要誠實：`SUCCESS` 是過度承諾

系統能保證的是「宣稱的驗證真的跑過且通過、變更沒有越界」，
不是「Agent 解對了問題」。

有個實測案例很說明問題：測試的期望值本身寫錯，Agent 就在實作裡加了 `+1` 去迎合它。
系統判定成功，機械上完全正確。

所以判定結果的正確語意是**「沒有發現任何不通過的證據」**，這跟「已證明完成」差很遠。

## 取捨類決策

### fail-closed，但「未知」不算失敗

安全判定要 fail-closed：evidence 缺失或不確定時，不得判成功。

但這條有個容易踩壞的邊界：**如果工具自己的解析能力不足也算失敗，
那這個機制會被使用者關掉，等於沒做。**

所以拆成兩條原則：

```text
不完整不等於通過    timeout、執行被中斷 → 不確定
未知不等於失敗      解析不出來、基準取不到 → 退回原本行為，但標示出來
```

差別在於：前者是「執行沒跑完」（事實），後者是「我看不懂」（能力限制）。
把自己的能力限制轉嫁成對方的失敗，是設計上的傲慢。

### 隔離的成本要有逃生口，而不是先做快取

pre-flight baseline 讓驗證時間翻倍。直覺是做快取，但快取需要持久化與失效邏輯，
是一整套新機制。

實測兩個真實專案分別是 12 秒與 0.6 秒，翻倍完全無感。
所以先提供一個關掉的開關，等真的有跑幾分鐘的專案再說。

**一般化的形式：** 成本問題先給逃生口，不要先給優化機制。
逃生口是十行，優化機制是一個子系統，而你還不知道成本是不是真的存在。

### 不可信的一方不能決定沙箱能看到什麼

驗證指令由被驗證的 repo 提供（它最清楚怎麼測自己），但：

- 指令必須是 argv 陣列，不是 shell 字串
- 執行檔不得是絕對路徑（不能指向 workspace 外）
- 沙箱要 bind 哪些 toolchain 路徑，由執行方的全域設定決定，不是 repo

分界線是：**repo 可以說「怎麼驗證我」，不能說「驗證時可以看到什麼」。**

## 那些差點做錯的

### 「沒有專用欄位」不等於「表達不了」

某個專案的測試需要環境變數才能跑，而驗證設定的 schema 沒有 env 欄位。
看起來是設定檔缺資訊的第一個真實案例，正要加欄位時發現：

```json
["env", "PYTHONPATH=app", "python", "-m", "unittest", "discover", "-s", "tests"]
```

`env(1)` 當第一個參數就解決了 —— 不是絕對路徑、不是 shell 字串、是純 argv 陣列，
完全符合既有的契約。

**在為 schema 增加表達力之前，先確認現有機制真的不夠。**
這個反射比任何一條設計原則都省事。

### 分類比統稱有用

遇到「測試需要網路」時，如果直接設計一個 network 例外機制，會做錯 ——
因為那底下至少有五種形態（自己起服務、連 localhost、連 Docker network、
連主機服務、需要外網），解法完全不同。

實際遇到的第一個案例是「連主機服務」。**一個案例不足以決定例外機制的形狀**，
所以只記錄不設計。

### capability 不等於 isolation

發現 Agent 的暫存目錄不可寫、驗證那邊可寫時，我的第一個判斷是
「驗證的隔離比 Agent 寬鬆，違反了設計規則」。

這是錯的。驗證那邊的暫存目錄是 private tmpfs，主機的暫存目錄對兩邊同樣不可見 ——
從安全邊界看沒有誰比誰弱。真正的問題是**執行語意不一致**，
導致 Agent 無法預演驗證會做的事。

「這是安全問題還是一致性問題」會導向完全不同的修法。判斷錯了，
會去修一個不存在的安全漏洞，而真正的問題（Agent 產生假失敗回報）還在。

## 流程類決策

### 已知限制是 watch list，不是 backlog

差別在心理壓力：backlog 會製造「應該把它做完」的感覺，watch list 不會。

但 watch list 需要**寫死的升級條件**，否則過幾週會退化成模糊印象：

```text
false ACCEPT / false BLOCK / 大量 retry / 無法完成重要工作 / 明顯操作成本
```

不符合任一條就維持觀察。**不為了把清單清空而實作。**

### 記錄機制要對準升級條件

工具會記下所有機械事實，但有一件事只有人知道：**它判錯了**。

所以加了一個記錄指令，分類直接對應上面五條升級條件 ——
不是通用的「意見箱」，因為通用的分類最後什麼都記，然後什麼都不能用來做決定。

### 停止驗證，開始使用

跨兩個 repo、10 個真實工作、核心零修改之後，繼續找第三個 repo 的資訊增益開始下降。

除非有天然符合壓力條件的目標（驗證要跑幾分鐘、且真的依賴外部服務），
否則不為了測試而找測試 —— 改成正常使用，讓下一個設計需求由真實工作逼出來。
