# 開發過程與每階段真正抓到的問題

#ai #agent #process #validation #dogfood #research

## 這是什麼

一個系統從設計文件到「可以日常使用」的完整過程紀錄。重點不在做了什麼功能，
而在**每一輪驗證活動實際抓到什麼** —— 這是判斷一個驗證方法值不值得的唯一依據。

## 核心結論

> 驗證活動的價值等於它抓到什麼。
> 每一輪開始前先問「這一輪要證偽哪個假設」，跑完後看它是否真的動搖了什麼。

四輪驗證，共抓到 8 個真實缺陷，其中 6 個是自動化流程自己抓出來的。

## 階段一：實作前的 spike

設計文件列了三個「必須實測、不可依賴文件假設」的阻擋項。照做之後：

| 假設 | 實測結果 |
|---|---|
| 沙箱模式擋得住網路 | **不成立** — curl 拿到 200 |
| Agent 看不到操作者的 HOME | **不成立** — `~/.ssh`、`~/.secrets` 全都讀得到 |
| 唯讀掛載足以保護憑證 | **不成立** — 唯讀照樣讀得到 API key |

三個裡有兩個半不成立。如果跳過 spike 直接照文件寫，會得到一個宣稱隔離但沒有隔離的系統。

**教訓：文件寫的是意圖，不是行為。安全相關的每一條都要有一次實際執行的輸出當證據。**

詳見 [Sandbox 隔離的實測邊界](note.html?slug=ai/agent-work-harness/sandbox-isolation-findings)。

## 階段二：E2E 場景（抓到 3 個）

依設計文件列的九個場景各寫一個可重複執行的腳本。抓到：

1. **輸出 schema 不合規格** — 強制結構化輸出時，`required` 必須涵蓋所有欄位，
   optional 要寫成 nullable。不照做整個請求 400，而且錯誤訊息在正常路徑上看不到。
2. **retry budget 少算一次** — 計算剩餘次數時沒把「當前這次 retry」算進去，
   導致 budget 永遠用不完。
3. **skill 沒有真的送進 runtime** — 用錯路徑組合，而且清理時會刪掉 runtime 自己的內建元件。

第 2 個特別典型：它是純邏輯錯誤，單元測試沒抓到是因為我測的是「規則對不對」，
而不是「規則被餵了什麼」。E2E 場景會經過完整的參數傳遞路徑。

## 階段三：Dogfood（抓到 3 個）

用這個系統改它自己的程式碼，十個真實工作（3 read / 5 write / 2 邊界）。

第一輪十個裡有六個失敗，**但系統的判定行為全都是對的** —— 它回報了 BLOCKED 和
verification FAIL，沒有謊報成功。壞的是兩個實作缺陷：

1. **需求解析誤判** — 「不要改動其他指令的輸出格式」被當成 read-only 宣告，
   整個 write 工作被降級，Agent 想寫檔被沙箱擋住。
   修法：read-only 宣告要求動詞後面不得接受詞。
2. **測試需要巢狀沙箱** — 我寫的測試會開一層沙箱，而驗證本身已經在沙箱裡，
   巢狀開不起來。修法：偵測後 skip 並說明原因。

第 2 個我還修錯過一次 —— probe 用最小參數，巢狀時仍會成功，所以 skip 沒生效。
**probe 必須走與實際使用完全相同的執行路徑**，否則它驗的不是同一件事。

### 這一輪最有價值的產物

Agent 在一個 read 工作中找出了兩個我沒發現的真實缺陷：判定器對某個 evidence
只攔 FAIL、缺失或不確定時仍可能判成功（沒有 fail-closed）；還有一個輸入參數
從頭到尾沒被使用（逾時後只要有可解析的結果就會走成功路徑）。

**用系統檢查自己，比預先想好題目更能找到真問題。**

## 階段四：跨 Repo 驗證（抓到 2 個 + 推翻 1 個預期）

換名字是刻意的：dogfood 驗的是「系統能不能治理工作」，這一輪驗的是
「它的假設在別的 repo 形態下還成不成立」。失敗的意義不同。

兩站各跑 5 個真實工作：

| 站 | 目標 | 規模 | 結果 |
|---|---|---|---|
| 1 | TypeScript 專案 | 36.6k 行、214 檔 | 5/5 收斂，核心零修改 |
| 2 | Python / RAG 專案 | 10k 行、有服務依賴 | 5/5 收斂，核心零修改 |

### 被推翻的預期

第二站初看很嚇人：測試檔裡有 Docker DNS 名稱、文件的執行方式是
`docker run --network container:<name>`。我的判斷是「這需要沙箱內不可能有的三件事」。

**實測推翻了它。** 逐一跑 21 個測試檔，全部通過，不需要任何服務 ——
那些 URL 只是 mock 參數，那段 docker run 是正式環境驗證而非單元測試。

如果第一眼就下結論並開始設計例外機制，會為一個不存在的問題付出複雜度。

### 抓到的兩個

1. **驗證的執行規模無法解析** — 兩個真實專案的測試 runner 都沒有可解析的摘要格式。
   沒有造成誤判（未知會退回原本行為），但新做的保護機制在真實專案上等於不存在。
2. **執行環境不一致** — Agent 的暫存目錄不可寫，驗證那邊可寫，
   導致 Agent 回報「測試沒跑完」而驗證判通過。實測連跑三次確認驗證是對的。

第 2 個我一開始判斷成「違反隔離規則」，後來修正為「執行語意不一致」——
兩者導向完全不同的修法，混淆會做錯決定。

## 一個貫穿全程的判準

每次撞到問題，先問：

> **這是核心假設錯了，還是設定檔少了資訊？**

實際跑出來有三種答案，第三種最容易被忽略：

```text
核心假設錯      解析執行規模的能力不足 → 但沒造成誤判，先觀察
設定少資訊      （目前為止一次都沒出現）
兩者都不是      需要環境變數 → env(1) 就能表達，不需要新欄位
```

第三種救了一個 schema 欄位。**遇到「表達不了」的時候，先確認現有機制真的不夠。**

## 從驗證專案到日常使用

四輪之後的狀態：

```text
核心抽象      跨兩種語言、兩種 domain、兩種 runner，零修改
已知限制      6 項，全部已觀察但尚未造成實際損害
需要修改核心   無證據
```

這時候該停止「為了測試而找測試」，改成正常使用，讓下一個設計需求由真實工作逼出來。

已知限制被明確標成 **observed limitations（watch list）而不是 backlog** ——
差別在於 backlog 會製造「應該把它做完」的壓力，watch list 不會。
搭配寫死的升級條件：

```text
false ACCEPT      判通過但實際是壞的
false BLOCK       正當的工作被錯誤擋下
大量 retry        因資訊不足而反覆重跑成為常態
無法完成重要工作   某類工作因為該限制根本做不了
明顯操作成本      為了繞過它必須反覆做額外的事
```

不符合任一條就維持觀察。為此在工具裡加了記錄機制，因為
**「它判錯了」這件事只有人知道，機器記不到**，而沒有記錄就只能憑印象決定要不要修。
