# Copilot runtime 移植 Rust：AI 協助大型重寫的重點整理

#knowledge #ai-agents #migration #rust #refactoring

原文翻譯見 [Github copilot runtime 移植到 rust 中文全文翻譯](note.html?slug=ai/github-copilot-runtime-rust-migration)。這篇是讀後整理，聚焦在「AI agent 對大型重寫幫了什麼、怎麼幫、要防什麼」，不重述文章細節。

## 一句話結論

43 萬行 TypeScript → 83 萬行 Rust，128 個 PR、14 週半、一位工程師主導；token 帳單約 12 萬美元加上約三週人力。這種規模的重寫在 agent 出現之前需要一個團隊一兩年，而且會輸給功能開發的優先權而不被批准。AI 帶來的不是「寫得更快」，而是**讓一整類原本不划算的專案變得可行**。

## AI 帶來的幫助

### 成本降到專案站得住腳

- 96% 的輸入 token 是快取讀取，價格低一個數量級。長時程自主 session 的經濟性靠這個成立；harness 要刻意維持穩定的提示詞前綴。
- 開發者不再一次做一件事：送出提示詞後去做別的，等待時間可以疊起來。

### 監督量級被放大

- 作者親手寫約 2,600 則訊息，推動了 138 萬則助理訊息、186 萬次工具呼叫，61% 的工具呼叫來自子代理。
- 人的角色上移：界定問題、劃邊界、選策略、裁決例外、把關合併。人的介入意圖前三名是「審查／測試／CI」、「質疑技術決策」、「推動做完整」，合計 63%。

### 探索與驗證做得比人多

- 工具呼叫中讀、搜、跑診斷是編輯的 10 倍。工作型態是迭代式調查，不是狂噴程式碼。
- 靜態型別編譯器是 agent 的快速回饋迴路，87% 的 `cargo check` 乾淨通過。但錯誤 84% 是機械性的（找不到名稱、缺方法、型別不符、trait 界限），借用檢查器只佔 1.7%——這是「任何靜態型別語言」的論據，不是 Rust 專屬。

### 平行化到人做不到的規模

- 3 萬行的 `session.ts` 由一個父 session 先讀 56 分鐘，再拆給 15 個子 session（各自 worktree、各自分支）加 5 個子代理，25 小時完成。
- 子代理拿去探索、編輯留在主代理：脈絡可以平行調查，變更集中才不互相衝突。
- 一個聊天 session 被當成「代理式互斥鎖」，統一發放 8 個 session 的建置權，避免筆電被 15 個並行建置卡死。

### 多模型交叉審查

- 每次 rebase 後用三個不同模型各開一個子代理逐行比對舊 TS 與新 Rust，迴圈到全部乾淨為止。
- Agent merge 自動處理 CI 失敗、審查留言、衝突；人只在最後一步抽查「它怎麼回應審查者」。

## 原地原子替換

文章選的移植策略，拆成兩個詞：

- **原地（in place）**：不開長壽 feature branch、不停工，直接在 `main` 上一塊一塊換。對照組是「大爆炸」：另外寫一套完整替代品，做完一次切換。
- **原子替換（atomic swap）**：每個 PR 把某元件的 TypeScript **刪掉**、同時放入 Rust，留一層薄殼（shim）讓還沒移植的呼叫端叫到 Rust。刪舊加新在同一個 commit，不存在雙版本並存的中間狀態。對照組是 A/B：兩份都留、旗標切換、信心夠了再刪。

```text
移植前          TS 呼叫端 ──▶ TS 元件 A
PR 合併後       TS 呼叫端 ──▶ 薄殼 ──▶ Rust 元件 A    （TS 元件 A 已刪）
呼叫端也移植後  Rust 呼叫端 ──▶ Rust 元件 A           （薄殼也刪）
```

為什麼這樣選：

- 主分支永遠可出貨，新 Rust 立刻在正式版被真的跑到，可分批 pre-release 用真實流量驗證。
- 不用維護兩份會分歧的程式碼。像 session 編排這種有可變狀態、雙向回呼、貫穿全系統的元件，根本做不到可熱切換。
- **意外的好處**：TS 被刪了，別人同時對那段 TS 的修改在 rebase 時必然衝突（一邊改、一邊刪），等於免費的「漏移植」偵測。
- 每個 PR 只換一個元件或切片，diff 小、好審查。

代價：需要暫時性互通層（napi-rs 薄殼），高峰時 2,019 個 N-API 匯出、3,356 個呼叫點，移植完全部要拆掉。

## 短命分支的邊界怎麼切

每個 PR 就是一條短命分支，合併即刪。文章沒給公式，但做法可以歸納成五條：

1. **依相依方向，由葉節點往內。** 先切沒人依賴、也少依賴別人的：純函式、內容排除、shell 工具、檔案系統操作；再來有狀態子系統、tools、hooks、模型 client、MCP；被所有人呼叫的骨幹最後。葉節點換掉只有它的呼叫端要薄殼，骨幹先換則到處要薄殼。
2. **一個 PR 的邊界等於一個可包薄殼的介面。** 有簡單 API 的元件切一刀就走；牽連太多的先在 TS 裡重構出介面再移植。切不出邊界時，先做一個邊界。
3. **大元件不是一刀，是一波。** MCP 走了七個 PR、tools 六個。順序大致是：純邏輯 → 狀態所有權 → 編排 → 移除退路 → 拆掉暫時薄殼。每步都是獨立可合併的 PR。
4. **邊界內要能自足驗證。** 既有 E2E 在每個 PR 上跑，測試本身不准改。切片大小的上限是：E2E 還能證明行為沒變。
5. **用衝突成本當回饋。** 主分支每週數百個 PR，分支越久、範圍越大，rebase 衝突越多（整場移植 rebase 了 2,496 次）。衝突數是切太大的直接訊號。

切錯的例子：作者同時由下而上切 `session.ts`、由上而下切「所有進入點」，兩條分支在同一個樞紐檔案迎面相撞，其中一個 agent 直接把對方 worktree 的改動抓走合併。教訓：**兩條並行分支不能共用同一個樞紐檔案**，非共用不可時要有裁決者（人或指定的協調 session）。

開分支前的檢查表：

- 這塊有沒有對外介面能用薄殼包住？沒有 → 先重構出來
- 它依賴的東西是否已經移植？不是 → 先做那些
- 現有 E2E 能不能單獨證明它行為不變？不能 → 先補測試
- 有沒有進行中的分支也會動同一個檔案？有 → 序列化，或指定誰先合

## 可帶走的做法

| 做法 | 原因 |
|---|---|
| 先翻譯，後重設計；禁止 agent 順手最佳化 | 同時改語言與行為，壞掉時分不清是誰害的；作者每次破例都後悔 |
| 目標要講死：「100% Rust，不留 TS 執行環境」 | 模糊指示會被讀成「只做熱路徑」，I/O 與編排被當範圍外 |
| E2E 測試是判準，agent 未經同意不准改 | 幾乎所有功能遺漏的回歸都源於 E2E 不足或被 agent 刪掉 |
| 逃生門放在 agent 拿不到的地方 | agent 曾自己貼 `schema-break-ok` 標籤讓 CI 過關，被人抽查才抓到 |
| 同一失效模式出現第二次就寫進指示、技能、eval | 個案修好，也修系統 |
| 內層迴圈（建置、測試速度）更重要 | agent 想與寫變快，建置測試佔比反而上升；多 worktree 並行時尤其明顯 |
| 子代理探索、主代理編輯 | 平行調查脈絡，變更集中才不互相衝突 |

## 該警惕的地方

- **能編譯不等於正確。** 所有已知回歸都通過編譯。典型模式：型別曖昧（TS 的 `number` 變成 `f64`，序列化成 `42.0` 讓強型別 SDK 拒收）、`||` 翻成 `unwrap_or` 丟掉空字串處理、成對操作只移了一半、環境性行為遺漏（時區、`CREATE_NO_WINDOW` 旗標）、生命週期與控制代碼比實例活得久、同步 napi 呼叫阻塞主執行緒。
- **agent 會把你暴露的能力全部當成可用。** `orchestrate` 技能沒人叫它用，它自己比對情境就載入了。你暴露的能力集合就是你可能得到的行為集合。
- **對等的 agent 需要裁決者。** 一方四度拒絕整合，另一方直接動手，拒絕毫無份量。
- **「自主執行」要為跨出自己分支的決定留例外。** 「別為設計細節吵我」會被聽成「併吞同儕也可以」。
- **靜態分析與 `unsafe` 都不是萬靈丹。** 158 個 `unsafe` 全在外部邊界（C ABI、系統呼叫、SQLite、dlopen），沒有一個回歸與 `unsafe` 有關；回歸都是編譯器管不到的合約、順序、遺漏。

## 套到產品開發：五個階段怎麼配合

文章講的是移植，但流程機制通用。差別只有一個：移植可以「刪舊加新」是因為新舊行為要求 100% 相同；功能開發的新行為本來就不同，所以這一招要換成 feature flag，其他照用。真正的前提是**你有辦法自動判斷一個小改動有沒有弄壞東西**；沒有的話先補判準，不是先切片。

跟敏捷的關係：原則相同（小步、快回饋、隨時可出貨），差在三點——粒度從 story 往下掉到 PR、瓶頸從「寫」移到「審查與判準」、執行者從人變成 agent 而人退到控制迴路。當產出不再稀缺，流程要圍繞「怎麼快速知道做錯了」而不是「怎麼少做」來設計。

### 兩層節奏

**外層：一個功能一次**

規劃只產出三樣東西：
1. 完成狀態——上線後使用者能做什麼、怎麼驗證。寫終點，不寫動作。
2. 切片順序——介面／資料 → 核心邏輯 → 外部整合 → UI 串接 → 放量 → 清理，並標出哪些片會動到同一個模組。
3. 判準——這功能靠哪些自動化測試守住？沒有的先補，這是第 0 片。

不細到每個 PR。只定終點、順序、什麼不准動（測試、旗標豁免）。估算一定錯（文章 13 萬行估成 43 萬行），細規劃越早做越浪費。

回顧在功能結束時做一次，看的是「哪種錯誤重複出現、哪個判準沒接住、哪段規劃估錯」，改成規則或補測試，餵回下一個功能的規劃。

**內層：一片一次，多片並行**

```text
片 A  規劃 ▶ 執行 ▶ 審查 ▶ 發佈(旗標關)
   片 B    規劃 ▶ 執行 ▶ 審查 ▶ 發佈(旗標關)
      片 C       規劃 ▶ 執行 ▶ 審查 ▶ 發佈(旗標關)
                                        ▶ 開旗標放量 ▶ 刪旗標
```

- **片規劃**（人定邊界，agent 細切）：只看眼前一波。人寫幾百字的任務描述——範圍、介面、對應哪個測試；agent 讀程式碼後提細切方案，人審方案。
- **執行**（agent 為主）：探索交子代理，編輯集中在主代理。多片並行各自 worktree，共用模組的片序列化。每片合進 main，行為躲在旗標後。
- **審查**（自動 + 人抽查）：CI、多模型交叉審查、schema／合約檢查自動跑。人只看三件事——它怎麼回應審查意見、有沒有動到測試或豁免標籤、方向對不對。
- **發佈**（自動、高頻）：片合併就出 pre-release，旗標關著對使用者無感。整波到齊後內部先開、再逐步放量。出問題關旗標，不 revert。
- **片級回顧**（即時）：不等功能結束。agent 貼了不該貼的標籤、測試被改、同類 bug 第二次——當下就改指示或加檢查。

### 階段之間傳什麼

| 從 | 到 | 傳什麼 |
|---|---|---|
| 外層規劃 → 片規劃 | 順序與邊界 | 這一波做哪幾片、哪些檔不能同時動 |
| 片規劃 → 執行 | 任務描述 | 範圍、介面、判準，幾百字 |
| 執行 → 審查 | PR | 小到能從 diff 看出問題 |
| 審查 → 發佈 | 綠燈 + 人抽查 | 自動合併，人只在最後一格 |
| 發佈 → 回顧 | 品質訊號 | issue、錯誤率、旗標開關後的指標 |
| 回顧 → 規劃 | 規則 | 寫進指示、測試、CI 護欄，改下一波的切法 |

### 把大工作切成小需求

切出來的每一塊都要能獨立合併、獨立驗證、合併後主分支仍可出貨。對每一片問：

| 問題 | 答「否」代表 |
|---|---|
| 單獨合併後 main 能出貨嗎？ | 邊界切錯，通常缺旗標或缺介面 |
| 出問題能從 diff 看出原因嗎？ | 太大 |
| 不等其他進行中的片也能合嗎？ | 相依方向錯，或介面沒先定 |
| 有對應的自動化檢查嗎？ | 先補判準 |
| 一個人／一個 agent 幾天內做得完嗎？ | 再切一波 |

跟傳統 story splitting 的差別：INVEST 講「每片對使用者有價值」，這裡多一個約束「每片對 main 無害」。兩者衝突時用旗標解——價值以「波」為單位交付，程式碼以「片」為單位合併。

PR 數量是切小之後的副產品，不是目標。以「每天很多 PR」為 KPI 會得到拆得很碎但彼此依賴的半成品；切不開時（文章的 `session.ts`）寧可一個大 PR 配更重的審查。

### 一句話

功能層級：規劃一次、回顧一次。片層級：規劃、執行、審查、發佈一直在流，回顧隨時插進來。人守終點、邊界、判準和最後一格；中間的量交給 agent 和自動化。
