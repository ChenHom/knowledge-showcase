# 從 AI 粗稿到領域核可：Decision Table 操作手冊

#decision-table #playbook #ai-assisted-testing #test-design

## 這是什麼

這是一份可逐步執行的 Decision Table Playbook。它讓開發者、QA、PM 或領域人員從 Acceptance Criteria（AC）與已確認的業務規則出發，使用 AI 整理候選內容，再透過固定的人工檢查與完成門檻，產出可追蹤、可核可、可直接轉成 Test Case 的 Decision Table。

這份手冊不承諾相同 Prompt 一定產生相同文字；它追求的是不同操作者都留下相同類型的中間產物、接受相同品質門檻，最後得到同等可用的表格。

## 核心結論

AI 產生的第一張表只是候選稿，不是規格。穩定品質來自以下控制點：

```text
固定輸入契約
→ 分離已知事實與未知問題
→ 定義可安排的 Conditions
→ 定義可驗證的 Actions／Oracle
→ 展開並收斂 Rules
→ 獨立驗證語意、公式與算術
→ 雙向追蹤與領域核可
→ 才能轉成 Test Cases
```

AI 負責整理、展開、重算與提出反例；人負責確認業務事實、風險、錯誤優先順序及「怎樣才算正確」。任何會改變預期結果的未知事項，都不能由 AI 依常識補完。

## 使用方式

### 角色

- 操作者：依本手冊維護產物，可以是開發者、QA 或 PM。
- 領域負責人：回答業務問題並核可 Conditions、Actions、Rules 與錯誤優先順序。
- 審查者：未參與初稿的人，負責獨立重算、反向追蹤與找反例。
- AI：只能根據提供的來源工作，不是領域決策者或核可者。

同一人可以兼任操作者與審查者，但第二輪驗證必須重新從來源和公式計算，不可直接接受第一輪 AI 的結果。

### 開始前最小輸入

至少準備一條 AC。能取得時一併附上：

- 業務詞彙與定義。
- 規則、限制、公式及錯誤碼。
- 正常、拒絕及歷史缺陷範例。
- API、UI 或現有測試所表達的既有行為。
- 規則來源、負責人及版本。

只有程式目前怎麼做，不代表那就是正確業務規則。程式行為與業務說法衝突時，必須建立待確認問題。

### 產物狀態

每項規則或問題使用以下狀態：

| 狀態 | 意義 |
|---|---|
| `CONFIRMED` | 有來源且經領域負責人確認 |
| `OPEN` | 尚未取得會影響結果的答案 |
| `ASSUMPTION` | 暫時假設，不能進入正式核可版 |
| `REJECTED` | 已確認不屬於需求或不採用 |

## 一頁流程

| 階段 | 主要問題 | 主要產物 | 不通過時 |
|---|---|---|---|
| 0 | 這題適合 Decision Table 嗎？ | 適用性判斷 | 改用或補上其他方法 |
| 1 | 我們確定知道什麼？ | 輸入基線、Open questions | 停止展開並取得答案 |
| 2 | 哪些條件會改變結果？ | Condition catalog | 刪除模糊或派生條件 |
| 3 | 每種結果如何驗證？ | Action／Oracle catalog | 補上精確值與觀察方式 |
| 4 | 條件組合會得到什麼結果？ | 候選 Rules | 標出未知、短路與不可達 |
| 5 | 哪些 Rules 值得保留？ | 收斂表、刪留紀錄 | 補邊界與高風險案例 |
| 6 | 語意與計算真的正確嗎？ | 驗證報告 | 修正或回到領域確認 |
| 7 | 規則與表格能雙向追蹤嗎？ | 追蹤矩陣 | 補來源、Rule 或 Oracle |
| 8 | 誰核可這一版？ | 凍結版本 | 不得標記 Ready |
| 9 | 如何變成測試案例？ | Rule-to-Test-Case mapping | 不得加入新業務答案 |

## 逐步操作

### 階段 0：判斷是否適用

#### 輸入

要驗證的 AC、業務決策或系統行為簡述。

#### 操作

確認結果是否主要由有限、可列舉的條件組合決定。若需求重點是下列問題，Decision Table 只能處理其中的決策切片：

- 效能、容量、壓力或長時間穩定性。
- 複雜狀態轉移及事件先後順序。
- 高併發、競爭條件或分散式失敗。
- 大量連續數值的數學性質。
- 視覺品質或主觀體驗。

#### AI Prompt

```text
根據下列需求，判斷它是否適合用 Decision Table 表達。

只能使用我提供的內容，不可補業務規則。請輸出：
1. 可以由有限條件組合決定的部分。
2. 不適合由 Decision Table 驗證的部分。
3. 建議搭配的方法，例如狀態機、timeline simulation、
   property-based testing、效能測試或併發測試。
4. 結論：適用、部分適用或不適用，並說明理由。

需求：
<貼上 AC 與來源>
```

#### 固定產出

| 項目 | 內容 |
|---|---|
| 判斷 | 適用／部分適用／不適用 |
| Decision Table 範圍 | 要涵蓋的決策 |
| 排除範圍 | 不能由表格證明的事項 |
| 搭配方法 | 其他必要驗證 |
| 來源 | AC 或規格識別碼 |

#### 人工檢查

- 表格範圍是否聚焦在一個明確決策。
- 是否把時間順序、併發或效能問題硬塞成布林條件。
- 排除範圍是否真的另有驗證方式，而不是被遺忘。

#### 完成條件

已明確記錄適用範圍與排除範圍；若判定不適用，停止本 Playbook，不繼續產表。

### 階段 1：建立輸入基線

#### 輸入

AC、詞彙、規則、限制、公式、錯誤碼、範例、現有行為及其來源。

#### 操作

將材料拆成：已確認事實、業務規則、範例、觀察到的現況與未知事項。每一項都記錄來源和狀態。程式現況只能標為觀察結果，除非領域負責人確認它就是規格。

任何未知事項若會改變 Condition、Action 或預期結果，建立 `OPEN-001` 形式的問題並停止進入下一階段。

#### AI Prompt

```text
你是規格整理員，不是需求決策者。請把下列材料拆成：
- 名詞與精確定義
- 已確認事實
- 業務規則與限制
- 公式或錯誤碼
- 正例與反例
- 僅觀察到但未確認正確的現況
- 會影響結果的未知問題

每一項必須引用來源。沒有來源或來源互相衝突時，建立 OPEN-編號，
不可依一般業界慣例補答案。最後指出哪些 OPEN 會阻止建立 Decision Table。

材料：
<貼上所有輸入及來源識別>
```

#### 固定產出

需求輸入表與 Open questions，格式使用本文「可複製模板」章節。

#### 人工檢查

- AI 是否把常見做法寫成已確認規則。
- 同一詞彙是否有兩種意思。
- 正例與反例是否和文字規則一致。
- 現有程式行為是否被誤當成需求來源。
- 是否存在會改變預期結果但未標成 `OPEN` 的問題。

#### 完成條件

所有輸入都有來源與狀態；不存在未標記假設；所有阻斷性 Open questions 已由領域負責人回答。

### 階段 2：產生候選 Conditions

#### 輸入

已確認的名詞、事實、規則、限制與範例。

#### 操作

列出會改變結果的最小條件集合。Condition 應是可以安排的測試輸入，或可以觀察的前置狀態，例如「商品數量」「訂單是否可付款」，而不是「資料有效」「計算正確」等把答案藏在條件裡的說法。

能從其他 Conditions 直接算出的值通常不是獨立 Condition。先保留原始輸入，再把衍生值放到 Action 或計算欄。

#### AI Prompt

```text
根據以下已確認規則，提出最小 Condition 集合。

每個 Condition 請列出：
- ID 與名稱
- 精確定義
- 型別及允許值域
- 測試如何安排或觀察它
- 來源
- 它會影響哪些結果

禁止使用「有效」「正確」「正常」「符合規則」等循環定義。
指出重複、可由其他條件推導、或其實是結果的候選項目。
遇到未知業務答案只建立 OPEN，不可自行選值。

已確認規則：
<貼上階段 1 產物>
```

#### 固定產出

Condition catalog，以及被刪除、合併或改寫的候選 Condition 紀錄。

#### 人工檢查

- 每個 Condition 是否能被安排或觀察。
- 值域是否足以表達門檻前、門檻值與門檻後。
- 名稱是否偷藏預期答案。
- 是否重複表達同一業務事實。
- 是否錯把衍生計算結果當作獨立輸入。

#### 完成條件

每個 Condition 都有明確定義、型別、值域、安排方式及來源；重複與派生條件已處理。

### 階段 3：定義 Actions 與 Test Oracle

#### 輸入

已確認業務承諾、錯誤碼、公式、副作用及 Condition catalog。

#### 操作

列出每個條件組合應產生的可觀察結果。Action 可以是回傳值、錯誤碼、狀態、金額、事件、資料寫入或「不得發生」的副作用。

把「成功」「正確計算」「妥善處理」改成可直接比較的值、公式或狀態。HTTP 200 通常不足以構成完整 Oracle。

#### AI Prompt

```text
根據已確認規則與 Conditions，建立 Action／Test Oracle catalog。

每個 Action 請列出：
- ID 與名稱
- 精確預期值、公式、狀態或錯誤碼
- 測試時的觀察位置
- 必須發生的副作用
- 不得發生的副作用
- 規則來源與核可角色

禁止只寫「成功」「失敗」「正確」「正常處理」。
如果正確答案或觀察方式未知，建立 OPEN，不可推測。

輸入：
<貼上階段 1 與階段 2 產物>
```

#### 固定產出

Action／Oracle catalog，以及所有無法觀察或尚未核可的 Oracle 清單。

#### 人工檢查

- 每個 Action 是否能直接成為 assertion。
- 是否只驗證表面結果，漏掉資料、事件、Queue 或外部呼叫。
- 是否同時確認不應發生的副作用。
- 公式、錯誤碼及優先順序是否有權威來源。
- 測試環境是否實際能觀察該結果。

#### 完成條件

每個 Action 都有明確預期與觀察方式；所有會改變結果的 Oracle 已由領域負責人確認。

### 階段 4：生成候選 Rules

#### 輸入

Condition catalog 與 Action／Oracle catalog。

#### 操作

展開可能的條件組合，為每一組填入預期 Actions。這一輪先求可見性，不急著刪減數量。對每個組合標記：有效、不可達、重複、無業務意義或待確認。

`-` 只能表示條件因已確認的短路規則而不再影響結果；它不能表示忘了填、AI 不確定或懶得展開。

#### AI Prompt

```text
依據 Condition 與 Action／Oracle catalogs 產生候選 Decision Table。

要求：
1. 不可靜默刪除條件組合。
2. 每列都要填入預期 Action，或明確標成 OPEN。
3. 每個「-」要說明是無關條件、短路規則或不可達狀態。
4. 多個失敗條件同時成立時，不可自行決定錯誤優先順序。
5. 列出不可達、重複及無業務意義的候選列及理由。
6. 每個結果都要引用 Oracle ID。

輸入：
<貼上階段 2 與階段 3 產物>
```

#### 固定產出

未收斂候選 Decision Table，以及不可達、重複、短路和 Open question 清單。

#### 人工檢查

- 每個組合是否都有結果或明確未知狀態。
- `-` 是否都有規則依據。
- 不可能組合是否真的受領域不變量排除。
- 多錯誤情境是否暴露出尚未定義的優先順序。
- AI 是否把兩個不同業務情境錯誤合併。

#### 完成條件

候選組合沒有空白解讀；短路、不可達與未知事項都有可審查的理由。

### 階段 5：用邊界與風險收斂

#### 輸入

候選 Decision Table、業務風險、使用頻率、歷史缺陷及事故。

#### 操作

保留能證明不同業務行為的 Rules，優先檢查：

- 空值與缺少必要輸入。
- 一般正常路徑。
- 門檻前、剛好門檻、門檻後。
- 最小與最大合法值。
- 最小非法值。
- 多條件混合情境。
- 多錯誤同時成立及錯誤優先順序。
- 歷史缺陷、高損失或高頻路徑。

不要用「排列完整」取代風險判斷。若組合爆炸，使用等價類別、邊界值、Pairwise 或拆成多張聚焦不同決策的表。

#### AI Prompt

```text
請收斂候選 Rules，但不可直接刪除而不留紀錄。

對每個 Rule 補上：
- 測試企圖：它要證明哪一項行為
- 保護的業務風險
- 與相鄰 Rule 的差異
- 保留或刪除建議及理由

至少檢查空值、正常值、門檻前後、最大合法值、最小非法值、
混合情境、多錯誤優先順序及歷史缺陷。
若兩列測試企圖相同，提出合併建議；若高風險承諾沒有 Rule，提出缺口。

輸入：
<貼上階段 4 產物與風險資料>
```

#### 固定產出

收斂後的 Decision Table、每個 Rule 的測試企圖與風險，以及完整刪留紀錄。

#### 人工檢查

- 每個保留 Rule 是否保護不同的行為或風險。
- 邊界三點是否合理，而非機械套用所有數值。
- 高風險規則是否至少有一個 Rule。
- 被刪除的組合是否有可回查理由。
- 表格是否太大，需要依決策責任拆分。

#### 完成條件

每個 Rule 都有獨特測試企圖；每項高風險業務承諾都有覆蓋；刪除不會造成不可說明的規格缺口。

### 階段 6：驗證語意、公式與算術

#### 輸入

收斂後的 Decision Table、來源規則與公式。

#### 操作

分五輪檢查，不能混成一句「請確認正確」：

1. 語意：規則是否被正確理解。
2. 公式：數學關係是否忠實表達業務語意。
3. 算術：從原始輸入逐列重新計算。
4. 邊界：相鄰值是否產生預期的行為轉換。
5. 跨列一致性：只有一個條件變動時，不相關結果不應漂移。

重算時從原始輸入開始，不把表格原有計算欄當作真值。

#### AI Prompt

```text
請驗證這張 Decision Table，不可直接修改業務規則。

分開輸出五份結果：
1. 語意檢查：用自己的話重述每條規則，標出可能的歧義。
2. 公式檢查：從文字規則推導公式，與表格公式逐項比較。
3. 算術檢查：只使用原始 Conditions 逐列重算，列出計算過程與差異。
4. 邊界檢查：比較門檻前、門檻值、門檻後的結果。
5. 一致性檢查：比較只差一個 Condition 的相鄰 Rules。

差異請列出 Rule ID、原值、重算值、依據及建議處置。
遇到語意不明時建立 OPEN，不可投票或猜答案。

來源與表格：
<貼上來源規則、公式與階段 5 產物>
```

#### 固定產出

驗證報告，逐項記錄檢查類型、Rule、證據、原值、重算值、結果及處置。

#### 人工檢查

- AI 是否誤解自然語言，例如把「每組第二件六折」理解成「第二件以後皆六折」。
- 公式是否涵蓋取整、稅、幣別、時間或順序規則。
- 每列數字是否真正重新計算。
- 錯誤優先順序是否經領域確認。
- 審查是否只由產生初稿的同一答案自我背書。

#### 完成條件

所有差異已修正或轉為明確 Open question；沒有未解釋的算術差異，也沒有只靠 AI 宣告正確的結果。

### 階段 7：完整性與可測性審查

#### 輸入

修正版 Decision Table、需求輸入表、Condition 與 Action catalogs。

#### 操作

執行雙向追蹤：

```text
需求／規則 → 哪些 Rules 證明它？
每個 Rule → 來自哪項需求、規則與 Oracle？
```

另外檢查 Condition 是否能安排、Action 是否能觀察、每個 Rule 是否能形成獨立 Test Case。未列出的情境只能標為範圍外，不能自動宣稱不可能。

#### AI Prompt

```text
請對 Decision Table 做雙向追蹤與可測性審查。

找出：
1. 沒有任何 Rule 覆蓋的已確認規則。
2. 沒有來源的 Condition 或 Action。
3. 沒有 Oracle 或無法觀察結果的 Rule。
4. 相同條件卻得到矛盾結果的 Rules。
5. 被當成不可能、但其實只是未列出的組合。
6. 無法轉成明確 Given／When／Then 的 Rule。

每項問題必須引用 ID 與最小反例，不可自行補需求。

輸入：
<貼上階段 1、2、3 與 6 的產物>
```

#### 固定產出

需求—Rule—Oracle 追蹤矩陣，以及完整性與可測性缺口清單。

#### 人工檢查

- 每項重要業務承諾是否至少有一個 Rule。
- 每個 Rule 是否能追溯到已確認來源。
- 表格是否把範圍外情境錯誤標為不可能。
- 測試是否能建立前置狀態並觀察完整結果。
- 是否遺漏負面副作用或錯誤優先順序。

#### 完成條件

所有重要需求皆可追蹤到 Rule；所有 Rules 皆可追蹤到來源與 Oracle；阻斷性可測性缺口已關閉。

### 階段 8：領域核可與凍結

#### 輸入

Decision Table、驗證報告、追蹤矩陣、刪留紀錄及 Open questions。

#### 操作

由領域負責人核可業務語意、預期結果、錯誤優先順序與適用範圍。記錄版本、日期、核可者、來源版本、限制及尚未解決但不阻斷本範圍的問題。

任何仍會改變現有 Rule 結果的 Open question 都是阻斷項，不能藏在附註中帶過。

#### AI Prompt

```text
請整理 Decision Table 核可包，不可替任何人核可。

輸出：
- 本版涵蓋與排除範圍
- Conditions、Actions、Rules 數量
- 已修正的語意或計算錯誤
- 刪除 Rules 及理由
- 未解 Open questions 與是否阻斷
- 需要領域負責人逐項確認的業務答案
- 版本、來源版本、日期與核可欄位

若資料不足，明確標成 NOT READY，不可使用模糊的「大致完成」。

輸入：
<貼上所有審查產物>
```

#### 固定產出

有版本識別的正式 Decision Table 與核可紀錄。建議狀態只有 `DRAFT`、`IN REVIEW`、`APPROVED`、`SUPERSEDED`。

#### 人工檢查

- 核可者是否有權決定相關業務規則。
- 核可範圍與排除範圍是否清楚。
- 是否仍有會改變結果的阻斷問題。
- 表格來源是否對應正確版本。
- 後續規則改變時，是否能知道哪一版失效。

#### 完成條件

核可者、版本、日期、來源、適用範圍、限制及問題狀態齊全；只有符合條件的版本能標為 `APPROVED`。

### 階段 9：轉成 Test Cases

#### 輸入

狀態為 `APPROVED` 的 Decision Table。

#### 操作

原則上每個 Rule 產生一個抽象 Given／When／Then Test Case：

- Given：Conditions 對應的前置狀態與輸入。
- When：AC 中的業務行為。
- Then：Actions／Oracle 對應的所有預期結果。

這一階段不加入 API endpoint、HTTP Header、DOM selector 或測試框架語法。若一個 Rule 必須拆成多個案例，或多個 Rules 可以合併成參數化案例，記錄映射關係及理由。

#### AI Prompt

```text
把已核可 Decision Table 轉成抽象 Test Cases。

要求：
- 每個 Rule 都必須出現在 Rule-to-Test-Case mapping。
- Given 只能使用該 Rule 的 Conditions。
- When 只能描述 AC 中的業務行為。
- Then 必須覆蓋該 Rule 的所有 Actions／Oracle。
- 不加入 endpoint、header、selector、測試框架或表格外的新業務答案。
- 合併、拆分或參數化時，記錄 Rule IDs 與理由。

輸入：
<貼上 APPROVED Decision Table 與 AC>
```

#### 固定產出

Rule-to-Test-Case mapping，以及框架無關的 Given／When／Then Test Cases。

#### 人工檢查

- 每個 Rule 是否至少對應一個 Test Case。
- 每個 Then 是否逐欄對應 Oracle。
- 是否遺漏不得發生的副作用。
- AI 是否在轉寫時新增業務答案。
- Test Case 是否仍保持抽象但不模糊。

#### 完成條件

所有 Rules 都有測試映射；測試輸入與預期結果能反查原表；沒有表格外的新規則。

## 完整案例：購物車結帳

### 原始 AC

- 啤酒單價 65 元，每兩件中的第二件六折，因此每組優惠 26 元。
- 可樂單價 18 元，綠茶單價 25 元。
- 每種商品最多購買 10 件。
- 空購物車不得結帳。

### AI 第一版粗稿

| Rule | 有啤酒 | 啤酒至少 2 件 | 有可樂 | 有綠茶 | 數量不超過 10 | 正確總額 | 拒絕結帳 |
|---|---:|---:|---:|---:|---:|---:|---:|
| R1 | 是 | 是 | 否 | 否 | 是 | 是 | 否 |
| R2 | 是 | 否 | 否 | 否 | 是 | 是 | 否 |
| R3 | 否 | 否 | 是 | 否 | 是 | 是 | 否 |
| R4 | 是 | 是 | 否 | 否 | 否 | - | 是 |

這張表格式像 Decision Table，但不能直接成為高品質測試規格：

- 「有啤酒」無法區分 1、2、3、4、10、11 件。
- 「啤酒至少 2 件」看不出有幾組優惠及奇數件如何處理。
- 「數量不超過 10」沒有說是哪一種商品。
- 「正確總額」沒有提供可驗證的金額或公式。
- 看不出空購物車、最大合法值及最小非法值。
- 每列沒有獨特測試企圖。

### 修正 Conditions

| ID | 名稱 | 型別／值域 | 理由 |
|---|---|---|---|
| C1 | 啤酒數量 | 非負整數 | 直接表達優惠與限購邊界 |
| C2 | 可樂數量 | 非負整數 | 檢查非優惠商品及通用限購規則 |
| C3 | 綠茶數量 | 非負整數 | 檢查混合商品及通用限購規則 |

布林分類不是永遠錯；問題是這裡的具體數量同時決定優惠組數、金額與限購結果，過早壓成 Y/N 會丟失測試所需資訊。

### 修正 Actions 與 Oracle

| ID | 名稱 | Oracle |
|---|---|---|
| A1 | 啤酒優惠組數 | `floor(C1 / 2)` |
| A2 | 未折扣總額 | `C1 × 65 + C2 × 18 + C3 × 25` |
| A3 | 總優惠 | `A1 × -26` |
| A4 | 結帳金額 | `A2 + A3` |
| A5 | 是否允許結帳 | 三種商品總數大於 0，且 C1、C2、C3 各自不超過 10 |

現在每個結果都有精確值，可以直接變成 assertion。

### 收斂後的 Decision Table

| Rule | 啤酒 | 可樂 | 綠茶 | 優惠組數 | 未折扣總額 | 總優惠 | 結帳金額 | 結果 | 測試企圖 |
|---|---:|---:|---:|---:|---:|---:|---:|---|---|
| R1 | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 拒絕 | 空購物車 |
| R2 | 1 | 0 | 0 | 0 | 65 | 0 | 65 | 允許 | 優惠門檻前 |
| R3 | 2 | 0 | 0 | 1 | 130 | -26 | 104 | 允許 | 剛好觸發一組優惠 |
| R4 | 3 | 0 | 0 | 1 | 195 | -26 | 169 | 允許 | 奇數件只形成一組優惠 |
| R5 | 4 | 0 | 0 | 2 | 260 | -52 | 208 | 允許 | 多組優惠累加 |
| R6 | 10 | 0 | 0 | 5 | 650 | -130 | 520 | 允許 | 最大合法值 |
| R7 | 11 | 0 | 0 | 5 | 715 | -130 | 585 | 拒絕 | 最小非法值 |
| R8 | 12 | 0 | 0 | 6 | 780 | -156 | 624 | 拒絕 | 超限判斷不是只寫死 11 |
| R9 | 0 | 5 | 0 | 0 | 90 | 0 | 90 | 允許 | 非優惠商品計價 |
| R10 | 0 | 0 | 4 | 0 | 100 | 0 | 100 | 允許 | 另一非優惠商品計價 |
| R11 | 2 | 3 | 0 | 1 | 184 | -26 | 158 | 允許 | 優惠與非優惠商品混合 |
| R12 | 3 | 2 | 4 | 1 | 331 | -26 | 305 | 允許 | 三種商品混合且啤酒為奇數 |
| R13 | 0 | 11 | 0 | 0 | 198 | 0 | 198 | 拒絕 | 限購規則適用非優惠商品 |
| R14 | 5 | 5 | 11 | 2 | 690 | -52 | 638 | 拒絕 | 混合購物中任一商品超限 |

這 14 列不是所有可能組合，而是用空值、門檻、邊界、商品類型、混合情境及規則一致性收斂出的代表案例。

### 人工審查如何抓錯

第一類是語意錯誤。AI 曾可能把「每兩件中的第二件六折」理解成第二件以後全部六折。用 R4 的 3 件啤酒可以區分兩種解讀：

```text
正確：一組優惠，65 + 39 + 65 = 169
錯誤：第二、三件都六折，65 + 39 + 39 = 143
```

第二類是算術錯誤。R14 必須從 Conditions 獨立重算：

```text
5 × 65 + 5 × 18 + 11 × 25
= 325 + 90 + 275
= 690

優惠組數 = floor(5 / 2) = 2
總優惠 = 2 × -26 = -52
結帳金額 = 690 - 52 = 638
```

若沿用 AI 初稿中的總額再請 AI「確認」，很可能只是在重複原錯誤；審查必須由原始數量和已核可公式重新計算。

### 從 R3 轉成 Test Case

```text
TC-03：兩件啤酒觸發一組優惠

Given
- 購物車內有 2 件啤酒、0 件可樂、0 件綠茶

When
- 使用者結帳

Then
- 優惠組數為 1
- 未折扣總額為 130
- 總優惠為 -26
- 結帳金額為 104
- 系統允許結帳
```

這裡仍未指定 API 或 UI 操作方式；後續探索階段才把抽象 Test Case 對應到具體操作。

## Definition of Done

只有以下各項全部成立，Decision Table 才能標為 `APPROVED`：

- [ ] 適用範圍與排除範圍已記錄。
- [ ] 每項輸入、規則及 Oracle 都有來源與狀態。
- [ ] 沒有未標記的 AI 假設。
- [ ] 每個 Condition 可安排或觀察，且有明確型別和值域。
- [ ] 每個 Action 可直接轉成 assertion。
- [ ] 必須發生及不得發生的副作用都已定義。
- [ ] 每個 Rule 有獨特測試企圖與風險。
- [ ] 空值、主要正常路徑及重要邊界已有適當覆蓋。
- [ ] 每個 `-`、短路或不可達組合都有理由。
- [ ] 多錯誤情境的優先順序已由領域負責人確認。
- [ ] 語意、公式與逐列算術已分開驗證。
- [ ] 計算結果從原始 Conditions 獨立重算。
- [ ] 每項重要業務規則可追蹤到至少一個 Rule。
- [ ] 每個 Rule 可追蹤到來源與 Oracle。
- [ ] 所有阻斷性 Open questions 已關閉。
- [ ] 核可者、版本、日期、來源版本與限制齊全。
- [ ] 每個 Rule 都能對應到 Test Case，且沒有新增表格外規則。

## 常見失敗與回退方式

| 症狀 | 問題 | 回到哪一步 |
|---|---|---|
| 表格工整但只能填 Y/N | Condition 過早抽象化 | 階段 2 |
| 結果寫「正確處理」 | 缺少 Test Oracle | 階段 3 |
| 大量組合無法 Review | 未用風險與邊界收斂 | 階段 5 |
| 同一輸入出現兩種結果 | 規則矛盾或優先順序未知 | 階段 1 或 6 |
| AI 每次算出不同數字 | 沒有固定公式或未獨立重算 | 階段 3 或 6 |
| `-` 無法說明 | 短路規則未定義 | 階段 4 |
| Test Case 多出新需求 | 轉寫時讓 AI 補規則 | 階段 9 |
| 需求改了卻不知道改哪裡 | 缺少雙向追蹤與版本 | 階段 7 或 8 |

## 維護規則

當 AC、公式、錯誤碼、限額或優先順序改變時：

1. 將既有核可版標成 `SUPERSEDED`，不要直接覆蓋歷史。
2. 從追蹤矩陣找出受影響的 Conditions、Actions、Rules 與 Test Cases。
3. 回到最早發生變動的階段重新執行，不只修改最終表格。
4. 重新完成語意、公式、算術、完整性及領域核可。
5. 記錄新版本與來源版本。

若只是 API endpoint 或 UI selector 改變，而業務輸入與 Oracle 未變，Decision Table 通常不需改版；應更新的是操作規格或自動化測試程式。
