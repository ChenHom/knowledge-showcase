AI 協作收斂：從大量資料表回到業務模型

#ai-collaboration #domain-modeling #database-design #architecture-decision #specification-engineering

這是什麼

AI 收到一段業務描述後，常先產生大量 entity 與資料表。語言模型傾向把每個名詞都實體化，再用「通用企業系統」慣例補齊歷程、設定、對照與稽核表。問題不在第一版發散，而在團隊是否有方法把它收斂。

核心結論

資料表不是需求的起點。先找業務不變量、交易邊界與生命週期，再決定持久化模型。若直接對著 AI 產生的表逐張討論欄位，團隊會被假精確拖走。

討論順序

先問每張表代表什麼責任

對每個候選表提出四個問題：

  • 它是否有獨立識別與生命週期？
  • 哪個業務規則必須由它維護？
  • 哪些命令會直接改變它？
  • 刪掉它後，哪項必要能力無法成立？

答不出來的表多半是過度正規化、技術偏好或假需求。

區分四種資料

| 類型 | 判斷方式 | 常見處理 |

|---|---|---|

| 核心交易資料 | 決定業務結果，需長期追蹤 | Entity / Aggregate |

| 快照資料 | 必須保留交易當下內容 | 內嵌欄位或 JSON 快照 |

| 衍生資料 | 可由其他資料重建 | 讀取模型、快取 |

| 設定與字典 | 低頻變更、被多處引用 | 設定檔或獨立表 |

AI 常把後三類全部拆成獨立 entity，導致 join、同步與一致性成本一起增加。

用生命週期合併

若兩個概念總是一起建立、一起刪除、不能獨立修改，也不會被其他流程引用，它們大概屬於同一個 aggregate 或 value object。若付款可獨立重試、退款與對帳，付款就不該只是訂單表上的幾個欄位。

用不變量切交易邊界

同一筆資料庫交易內必須原子成立的規則，通常應由同一 aggregate 維護。跨 aggregate 的一致性改用事件、冪等與補償，不應假裝所有事都能靠一個巨大 transaction 解決。

最後才談查詢與效能

寫入模型服務業務一致性；報表與搜尋可用獨立讀取模型。為了某張後台列表把所有概念塞進一張主表，只是把短期查詢方便換成長期耦合。

三輪 AI 對話

第一輪要求逐張提出存在證據：

針對目前候選表逐張說明：
1. 它維護哪條不變量。
2. 是否具有獨立生命週期。
3. 若合併或刪除，會失去哪個已確認需求。
4. 哪些欄位只是快照、衍生值或未確認假設。
不得以「未來可能擴充」作為保留理由。

第二輪要求最小模型，列出刪除、合併、延後、保留及證據。第三輪再用取消、重試、部分失敗、重複通知、併發更新與稽核需求攻擊最小模型，只補回有具體反例證明需要的結構。

收斂表

| 候選概念 | 決定 | 依據 |

|---|---|---|

| Order | 保留 entity | 有獨立狀態與付款不變量 |

| OrderAddress | 合併為快照 | 不會獨立修改，需保存交易當下內容 |

| OrderStatusHistory | 延後 | 已有 domain event log，現階段沒有獨立查詢需求 |

| PaymentAttempt | 保留 entity | 可重試、可失敗，生命週期不同於 Order |

| Currency | 設定／字典 | 不維護交易狀態 |

| DashboardSummary | 衍生讀取模型 | 可由事件或交易資料重建 |

人與 AI 的分工

AI 負責產生候選、比較方案、找反例與維護追蹤表。人負責確認需求是否真實、規則優先順序、可接受風險與何時停止設計。「未來可能需要」不是需求證據。
